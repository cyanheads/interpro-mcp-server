# interpro-mcp-server

## MCP surface

| Tool | Purpose |
|:--|:--|
| `interpro_search_entries` | Find InterPro entries by GO annotation, or entries and member signatures by text, type, or integration. |
| `interpro_get_entry` | Read one entry's complete metadata, description, hierarchy, annotations, and coverage. |
| `interpro_get_protein_domains` | Map a protein's domains, families, repeats, and functional sites to sequence coordinates. |
| `interpro_get_clan` | Read a Pfam, CDD, or PIRSF set and page through its members. |
| `interpro_find_proteins_by_domain` | Find proteins carrying an entry, defaulting to reviewed human proteins. |
| `interpro_list_reference` | Decode database slugs, identifiers, entry types, taxa, and release information. |

All six tools are read-only and idempotent. Set `readOnlyHint: true`, `idempotentHint: true`, and `openWorldHint: true`; the reference tool also has a live release branch. Use `auth: ['tool:<tool_name>:read']` consistently for deployments enabling framework authentication. No resources, prompts, or app tools are needed: every workflow has a tool path. InterProScan sequence submission is outside this surface.

## Requirements and workflows

The source is the keyless [InterPro API](https://www.ebi.ac.uk/interpro/api/), covering InterPro and its member databases. Support npm installation, STDIO, Streamable HTTP, and Docker. No operator credential or server-specific environment variable is required. Use stateless HTTP sessions.

1. Find an entry with `interpro_search_entries`, then pass its accession to `interpro_get_entry`.
2. Pass a UniProt accession and optional residue position to `interpro_get_protein_domains`; distinguish domain/site matches from broader family matches by their retained entry type.
3. Follow an entry's `set_info.accession` through `interpro_get_clan`, then retrieve individual member entries when needed.
4. Pass an entry accession to `interpro_find_proteins_by_domain`; change the echoed human/reviewed defaults deliberately.

Coordinates describe sequence annotation, not pathogenicity or clinical significance. An absent match does not establish absence of biological function.

## Shared contracts

### Vocabulary and validation

`sourceDatabase` is one of `interpro`, `pfam`, `prosite`, `profile`, `smart`, `cdd`, `panther`, `cathgene3d`, `ssf`, `ncbifam`, `hamap`, `prints`, `pirsf`, `sfld`, `antifam`. PROSITE has separate pattern/profile API slugs. MobiDB-Lite belongs to protein extra features, not this entry enum. InterPro is the integrating database; AntiFam is an additional API source. Do not describe these 15 API slugs as 15 consortium members.

`entryType` is `domain`, `family`, `repeat`, `homologous_superfamily`, `active_site`, `binding_site`, `conserved_site`, `ptm`, `region`, `coiled_coil`, or `disordered`: every type `/entry/?group_by=type` reports. AntiFam entries carry `region`. `goCategory` is `P`, `F`, or `C`; `goTerm` matches `^GO:\d{7}$`. `taxonId` is a positive decimal string of at most 10 digits (NCBI taxon IDs run to 7 today), not a scientific name; the cap applies after trimming and rejects a longer value as an argument error before it reaches URL construction. All integers reject fractions. Trim strings; preprocess blank optional strings to `undefined` before validation, with `.describe()` on the outer wrapper, so a blank string field that carries a default (`sourceDatabase` on search, `taxonId` on discovery) takes it. Number and boolean fields stay unwrapped: a preprocess there would stop the framework from repairing `"5"` to `5`, so a blank string sent for one is a type error. Every schema field has a description.

Infer entry database case-insensitively from these anchored patterns; emit canonical case in derived accessions while retaining upstream metadata unchanged:

| Prefix/pattern | Source | Canonical example |
|:--|:--|:--|
| `IPR` + 6 digits | interpro | `IPR011615` |
| `PF` + 5 digits | pfam | `PF00870` |
| `PS00` + 3 digits | prosite | `PS00107` |
| `PS5` + 4 digits | profile | `PS50011` |
| `SM` + 5 digits | smart | `SM00220` |
| `cd` + digits | cdd | `cd08367` |
| `PTHR` + digits, optional `:SF` + digits | panther | `PTHR11447` |
| `G3DSA:` + four dot-separated nonnegative decimal components | cathgene3d | `G3DSA:3.30.200.20` |
| `SSF` + digits | ssf | `SSF56112` |
| `TIGR` or `NF` + digits | ncbifam | `TIGR00001` |
| `MF_` + digits | hamap | `MF_00001` |
| `PR` + digits | prints | `PR00386` |
| `PIRSF` + digits | pirsf | `PIRSF000047` |
| `SFLD` + optional letter + digits | sfld | `SFLDF00001` |
| `ANF` + digits | antifam | Consult the accession returned by search. |

These are routing patterns, not claims that every matching accession exists. Permit zero-valued components in CATH identifiers. An explicit `sourceDatabase` must agree with a recognized prefix; reject conflicting routes locally rather than disguising them as a missing entry. For a safe nonstandard identifier, an explicit source permits `[A-Za-z0-9_.:-]{1,100}` and skips inference, but exact `.` and `..` are invalid arguments. Reject slashes, backslashes, percent escapes, query/fragment delimiters, and control characters rather than decoding them. Encode each validated accession as one path segment; `encodeURIComponent` alone does not protect dot segments. Apply this rule to entry, set, and discovery targets. A `CL`/`cl` accession (any case) names a Pfam or CDD set, never an entry: the entry tools reject it before any request as `entry_not_found`, with a message and a throw-site recovery hint pointing to `interpro_get_clan` in place of the declared `entry_not_found` recovery. PIRSF accessions share one shape across entries and sets, so they route normally. No speculative alternate-source retry on 204: standard PROSITE prefixes already determine the route. UniProt inputs accept the documented six- or ten-character accession grammar, case-insensitively; reject isoform suffixes because these endpoints address canonical proteins.

### Output and rendering

All tools return a flat object schema. Validate required wire structure at the network boundary; allow additional JSON fields inside upstream records so a new annotation is preserved. Output types explicitly model nulls and omitted fields. Do not turn missing genes, names, GO annotations, descriptions, scores, or counters into invented empty values. A null is retained as null; an omitted field stays omitted. Proven empty collections and server-owned paging metadata may use empty arrays/zero/false.

Use the following reusable wire shapes:

- `EntrySummary = { accession, name: string|null, source_database, type, integrated?: string|null, member_databases?: record<database, record<accession,string>>|null, go_terms?: GoTerm[]|null, ...additionalJson }`.
- `GoTerm = { identifier, name, category: { code, name }, ...additionalJson }`.
- `EntryMetadata` preserves the complete detail endpoint's `metadata`: `accession`, `entry_id`, `type`, `source_database`, object-valued `name`, `description` objects (including `text`, `llm`, `checked`, `updated`), `hierarchy`, `integrated`, `member_databases`, `go_terms`, `set_info`, `literature`, `cross_references`, `overlaps_with`, `counters`, and every additional JSON field. These detail fields differ from list summaries; do not reuse a string-only name schema. Literature may be an accession-keyed object or null. Preserve description HTML and citation markers verbatim as source text.
- `Location = { fragments: [{ start: positiveInteger, end: positiveInteger, 'dc-status'?: string, ...additionalJson }], representative?: boolean|null, model?: string|null, score?: number|null, ...additionalJson }`. Never flatten locations into a single interval or discard fragment discontinuity, model, representative flag, or upstream score.
- `ProteinSummary` retains accession, name, length, source database, `source_organism` (`taxId`, `scientificName`, optional `fullName`), optional/null gene, and AlphaFold flag when supplied. Protein detail includes additional fields such as sequence and counters; preserve the complete received metadata in the protein-map result.

List wire envelopes are `{ count: nonnegativeInteger, next: string|null, previous: string|null, results: [...] }`; search rows wrap summaries in `metadata`, while match rows additionally carry `proteins`, clan-member rows carry `sets`, and discovery rows carry `entries` and `taxa`. Unwrap only where the domain output explicitly requests it. Detail responses wrap the record in `metadata`; extra-feature responses do not. Entry detail `name` is an object with optional/null `name` and `short`, not a list-summary string. Require only routing/structural fields needed by the operation (accession, source database, record wrappers, and coordinate arrays); annotation fields listed above are optional and nullable where supplied that way. Model nested arbitrary JSON with recursive JSON-value schemas, not `any`, and preserve unknown fields. Locations need nonempty fragments with `start <= end`; extra-feature fragments may carry `seq_feature` without `dc-status`. A match without usable coordinates is an upstream shape error, never a fabricated interval or silent omission.

Every result includes `sourceUrl` or `sourceUrls` identifying its official sources, and a canonical website `url` where applicable. A shared formatter emits the **entire output as compact, unindented JSON in a fenced block**, then an index rendering every absolute HTTP(S) URL as a usable Markdown link. Only a value that is wholly an image renders as one: an HTTP(S) URL whose path ends in an image extension, or a base64 PNG, JPEG, or GIF data URI; a URL found inside prose is a link only, since clients fetch images unprompted, and any other data URI stays JSON data. No index destination may span a line. This handles large Pfam records without brittle table truncation. The JSON block is a reversible representation, not an abbreviated preview: parsing it must equal the handler output. Choose a fence longer than any backtick run in the serialized value. Escape link labels/destinations without changing the parsed URL; do not execute upstream HTML. `interpro_get_entry` and `interpro_get_clan` take `includeThumbnail=false`: by default each Wikipedia page's non-empty `thumbnail` string is removed from the domain output before either surface is built, every other Wikipedia field is kept, and an enrichment notice states how many thumbnails and bytes were omitted and names `includeThumbnail: true` as the way to get them; no notice is written when nothing was present. With `includeThumbnail: true`, convert a thumbnail that is wholly base64 PNG, JPEG, or GIF data (recognized by its signature) to its equivalent `data:image/<type>;base64,...` URI in the domain output and render it in the image index; the image is one indivisible item and is never truncated. Never truncate a string, array, hierarchy, relationship record, image, or rendered row, or let the two surfaces differ; size-bounded results (protein-map segments, relationship slices) return whole records on both surfaces and name the call that continues them, and an omitted thumbnail is disclosed in a notice.

Success context belongs to an `enrichment` declaration: optional `notice` (string), optional `totalCount` (number, the field written by `ctx.enrich.total()`), optional `truncated` (boolean), optional `shown`/`cap` (integers), and optional `effectiveQuery` (string, the field written by `ctx.enrich.echo()`). Use framework kind tags/helpers and render structured fields explicitly if introduced. All enrichment keys remain optional, disjoint from domain output; this avoids mandatory-key failures on ordinary, empty, and reference branches. Pagination results write total and echo on every success. Set truncation from actual continuation, not merely `results.length === limit`. A complete page exactly at its cap is not incomplete. For a partial result call `ctx.enrich.truncated({ shown, cap, guidance })`, with guidance naming the continuation: the same arguments with `cursor` set to `page.nextCursor`, and a larger `limit` only while the current one is below the tool's maximum. `truncated()` writes `notice` last-wins, so a tool with other notices composes them into that one guidance string. Expose continuation in domain output too. No fixed follow-up suggestions are needed when returned identifiers already support the next call.

### Pagination

`Page = { total: nonnegativeInteger, returned: nonnegativeInteger, limit: positiveInteger, hasMore: boolean, nextCursor?: string }`. Clamp positive integer limits to 100 for search/member pages and 50 for discovery, retaining default 20. The request `page_size`, `page.limit`, and enrichment `cap` use the effective size; compose requested/effective disclosure with empty-page, continuation, thumbnail, and relationship notices. Never suggest raising an effective maximum. Derive `hasMore` from upstream `next`; a response with no next omits `nextCursor`. A 204 list becomes total/returned zero, `hasMore: false`, and no cursor. Preserve the applied filters in a typed `query` object and echo them through enrichment.

Expose an opaque versioned base64url cursor envelope containing `{ v: 1, operation, scope, upstreamCursor }`. `scope` is the canonical tool query excluding cursor, page limit, the position input `relationshipOffset`, and the clan's `includeThumbnail` projection; callers may change those but not filters or target. Decode with a 4096-character maximum and validate all fields. The protein map resumes inside an upstream page, so its envelope carries `position` in place of `upstreamCursor`: `{ page?, skip, after? }` means `skip` records into the page whose upstream cursor is `page` (absent for the first page), and `{ features, after?, totalMatches }` means `features` selected extra features into the list that follows the last match. `after` names the last record an earlier segment covered; a position whose `after` no longer names the record before it, or that lies at or past the end of its page or feature list, is `invalid_cursor`. An envelope carries exactly one of `upstreamCursor` and `position`. This is a consistency token, not an authorization token. Extract only the `cursor` query value from upstream `next`, including values such as `source|s|pf00069`; never fetch an upstream next URL or copy its host, path, or unrelated query parameters. Construct every request against `https://www.ebi.ac.uk/interpro/api/` from validated inputs. Reject a next URL without a nonempty cursor as `upstream_shape_invalid`; detect repeated cursors during internal traversal. Cursors are not snapshots and may expire across upstream releases.

## Tool details

### interpro_search_entries

Description: “Search InterPro entries or member signatures by text or entry type. GO filters require sourceDatabase interpro; integratedInto selects member signatures for an InterPro accession. Results are cursor-paged; use interpro_get_entry for full metadata.”

Input: `sourceDatabase=interpro`; optional `query` (1–300 characters), `entryType`, `goTerm`, `goCategory`, `integratedInto` (IPR accession), and `cursor`; `limit=20` (positive integer, clamped to 100). No filter is required: omission intentionally browses the selected database. `integratedInto` requires a member source, not `interpro`. GO fields require `sourceDatabase=interpro`; reject a member combination as `go_filters_require_interpro` before any request. Recover by searching InterPro with the GO filter, then reading `member_databases` with `interpro_get_entry` or searching the member database with `integratedInto`. Other optional filters combine using upstream semantics; no free-form query-parameter object.

GET `/entry/{sourceDatabase}/`, allowing only `search`, `type`, `go_term`, `go_category`, `integrated`, `page_size`, `cursor`. Map input names explicitly. Output `{ query, entries: EntrySummary[], page: Page, sourceUrl }`; list metadata already carries member signatures/GO terms when available. No N+1 detail enrichment. A 410 is `entry_withdrawn`.

Zero hits: success plus “No entries matched the applied filters. Remove query, entryType, goTerm, goCategory, or integratedInto filters that are present; call interpro_list_reference with topic databases to check sourceDatabase.” For a member accession supplied as text under InterPro, add “Use interpro_get_entry with the accession to infer its member database.”

### interpro_get_entry

Description: “Retrieve one InterPro or member-database entry, including description, hierarchy, member signatures, GO terms, literature, cross-references, clan membership, and coverage counters.”

Input: required `accession`; optional `sourceDatabase`; `includeThumbnail=false`. GET `/entry/{resolvedDatabase}/{accession}/`. Output `{ accession, sourceDatabase, entry: EntryMetadata, url, sourceUrl }`, with Wikipedia thumbnails projected as described in Output and rendering; the only enrichment field is the thumbnail-omission `notice`. Retain counters under their actual names: `structural_models` is not silently renamed to AlphaFold. The upstream can supply null hierarchy, literature, member databases, set information, and GO annotations on valid members.

Entry detail alone adds optional `entry.descriptionText`, decoding HTML fragments while retaining raw null/string/array descriptions and annotation flags. The streaming `htmlparser2` tokenizer preserves text and entities, paragraph/list/table boundaries, and visible citation/accession tokens; href-only IPR/PUB references follow their labels unless already visible. Script/style text and event attributes contribute no readable text. Missing textual content omits the derivative. No article-selection heuristic, linked-page fetch, or unrelated output budget is introduced.

204/404 means `entry_not_found`; 410 means `entry_withdrawn`, retaining the available accession, deletion date, short name, and history in error data and naming the accession, deletion date, and short name in the message; `data.accession` is the canonical accession the message names, not upstream's spelling of it. Upstream text never shapes the message: it names an upstream accession, date, or short name only when the value matches a bounded single-line form (exactly an accession; `YYYY-MM-DD` with an optional `T` time; `[A-Za-z0-9_.:+-]{1,100}`), and leaves out the clause otherwise, so a crafted value cannot add a `Recovery:` line, a heading, or inline Markdown to the error text. The raw value stays in `data`. Never parse a 204 body as JSON.

### interpro_get_protein_domains

Description: “Retrieve InterPro and member-signature matches on a canonical UniProt protein, preserving every location and discontinuous fragment. Optionally retain matches covering a residue and include extra predicted features. Large maps arrive in segments of whole matches that fit the response budget: the first segment carries the protein metadata, requested extra features follow the last match, and coverage.nextCursor continues until hasMore is false.”

Input: required `accession`; optional `residuePosition` (positive integer); `includeExtraFeatures=false`; optional `cursor`. Fixed match page size 200. Read `/protein/uniprot/{accession}/` first, then `/entry/all/protein/uniprot/{accession}/?page_size=200`. On each invocation read at most three match pages; stop sooner when `next` is absent or when the matches already read fill the response budget. A continuation call rereads metadata and the page its cursor resumes inside, and returns only its own segment, never duplicating earlier items. With extras enabled, read `/protein/uniprot/{accession}/?extra_features` only in a call that reaches the end of the match list with budget to spare, or that resumes inside the features. Maximum five upstream operations before retries; the total deadline still wins.

Output `{ accession, protein?: complete protein metadata, matches: [{ metadata: EntrySummary, proteins: complete upstream protein-match objects }], extraFeatures?: record<featureKey, { accession, source_database, locations: Location[], ...additionalJson }>, selection: { residuePosition?: number, includeExtraFeatures }, coverage: { totalMatches, scannedMatches, returnedMatches, totalFeatures?, returnedFeatures?, complete, hasMore, nextCursor? }, url, sourceUrl }`. Preserve `protein_length`, source organism identifiers, and every nested `entry_protein_locations` field. `extra_features` responds as a feature-keyed object, not a protein metadata wrapper; keys may include FunFam identifiers in addition to disorder/transmembrane predictors.

The map is one walk: every match, in upstream page order with each page sorted by earliest fragment start, then accession in code-unit order, then canonical JSON, followed when requested by every selected extra feature in feature-key order. The sort makes a page split the same way however upstream orders it, so an offset into a reread page names the same record. Each call returns the longest run of whole items from its resume point that keeps the domain output, serialized as compact JSON, within `RESPONSE_BYTE_BUDGET` (see Budgets), and at least one item while any remain. A match or feature is never split; every location and fragment stays with its record. An item that cannot share a segment within the budget, in practice a single match larger than it, is returned alone with a notice that names it when its accession or feature key is exactly an accession and otherwise says “This match” or “This extra feature”; the record itself is in the JSON. `protein` appears only on the first segment (the call without cursor). `extraFeatures` appears on a segment that returns features, and as `{}` on the segment that ends the walk when no feature is selected, always with `totalFeatures` and `returnedFeatures`; it is omitted when not requested or when the segment ends before the features. Matches within a segment are presented sorted by earliest fragment start, then accession; that order is local to the segment, not a promise of global sequence order.

Coordinates are 1-based and inclusive. A residue filter retains a match when **any** fragment contains the position, but keeps that match's entire locations/fragments unchanged, including its other segments. Apply the same containment rule to extra features, retaining complete selected features. Validate position against fetched protein length; reject an out-of-range position. Do not infer overlap across a gap between discontinuous fragments. Filtered-out matches cost no budget.

`coverage.totalMatches` is the upstream unfiltered count; a segment holding only extra features repeats the count its cursor carries. `scannedMatches` counts the match records this segment covered before residue filtering, so the segments of a complete walk sum to `totalMatches`, and `returnedMatches` is this segment's selected match count. `coverage.complete` is true only when this invocation started without a cursor and returned the whole walk: every match and every requested extra feature. It remains false for every resumed segment, including the last one; `hasMore: false` on that segment means only that the walk reached its end. `hasMore` is true while matches or requested features remain, exactly when `nextCursor` is present. Cursor scope includes the canonical accession, residue selection, and extras flag.

When a segment stops with more to read, return a valid partial result whose notice states why (the response budget or the three-page limit) and names the exact next call: “This segment covers part of the protein map … Continue with interpro_get_protein_domains {…} before concluding that a residue has no annotation.” On a final resumed segment, explain that only the combined segments cover the traversal, and upstream pagination is not a snapshot; resumed segments also say that they omit the protein metadata the first segment returned. A later page failure is an error, never an apparently complete earlier subset. Only a complete first invocation may claim “protein has no returned signature matches” or “no match contains this position”; an empty partial/resumed segment means no match in this segment. Extra features do not alter match totals. An extras request that fails fails the call; omission means not requested or not reached, while `{}` means successfully fetched with no selected features (possibly after residue filtering).

Examples verified against the API: `P04637`, position 175, retains `IPR011615` and `PF00870`, both 100–288. `P00533`, position 858, retains kinase domain `IPR000719` (712–979); it excludes site entries `IPR008266` (833–845) and `IPR017441` (718–745). These examples make no assertion that every overlapping annotation is a domain.

### interpro_get_clan

Description: “Retrieve a Pfam, CDD, or PIRSF clan/set and a cursor page of member entries; optionally include its relationship graph, returned in slices that fit the response budget and paged with relationshipOffset.”

Input: required `accession`; optional `sourceDatabase` restricted to `pfam|cdd|pirsf`; `includeRelationships=false`; `relationshipOffset=0` (integer ≥ 0; a value above 0 is accepted only with `includeRelationships: true`); `includeThumbnail=false`; `limit=20` (1–100); optional `cursor`. Infer `CL` + digits → Pfam, `cl` + digits → CDD using case-sensitive prefixes because these identify different databases; mixed-case variants need explicit source. `PIRSF` + digits → PIRSF. An explicit Pfam/CDD source disambiguates case variants of the CL family; canonicalize to uppercase Pfam or lowercase CDD. PIRSF identifiers require the PIRSF source.

GET `/set/{database}/{accession}/`, then `/entry/{database}/set/{database}/{accession}/?page_size={limit}`. Output `{ accession, sourceDatabase, clan: metadata excluding relationships unless requested, relationshipsIncluded: boolean, relationshipsPage?: RelationshipsPage, members: complete upstream member records, page: Page, url, sourceUrl }`. Clan metadata retains description (possibly null), authors, literature, Wikipedia, and counters. Clan Wikipedia pages can carry a base64 thumbnail (a JPEG on `CL0159`); it follows the `includeThumbnail` projection in Output and rendering, its omission notice joins the clan's other notices, and because the flag shapes only the clan metadata reread on every page, it stays out of the member cursor scope. Member records retain `metadata` and `sets`. The metadata endpoint already returns relationships, so the switch controls projection on **both** output surfaces rather than upstream bandwidth. Echo that omission. 204/404 on the clan lookup is `clan_not_found`; 204 on members is a valid empty page. A 410 is `entry_withdrawn`.

When requested, `clan.relationships` holds one slice of the graph in the upstream `{ nodes, links }` shape. Every record in it is whole and verbatim, with all scores, methods, and nested flags; never synthesize a similarity score. Slices address one sequence: every node sorted by `accession`, then every link sorted by `source`, `target`, and `method`, with canonical JSON breaking any remaining tie, so an offset names the same record whatever order the upstream arrays arrive in. `relationshipOffset` is the position of the first returned record. Each call takes the longest run of whole records from there that keeps the domain output, serialized as compact JSON, within `RESPONSE_BYTE_BUDGET` (see Budgets), and at least one record while any remain. `RelationshipsPage = { totalNodes, totalLinks, offset, returnedNodes, returnedLinks, hasMore, nextOffset? }` appears only with `includeRelationships: true`, and `nextOffset` is present exactly when `hasMore` is true. While records remain, the notice names the next call: the same arguments with `relationshipOffset: nextOffset`. An offset at or past the end returns an empty slice and a notice, not an error. A null or absent upstream graph stays as supplied and pages as zero records; a graph without node and link arrays is `upstream_shape_invalid`, but only when requested. When the clan metadata and member page alone fill the budget (an opted-in thumbnail can), the slice still holds one record, and the notice names `includeThumbnail: false` or a smaller `limit`. `relationshipOffset` is a position like `limit`, so it stays out of the member cursor scope and member paging is unchanged. Without `includeRelationships: true`, `relationshipOffset: 0` is a no-op, since its only reading is the start of a graph that was not requested; a value above 0 fails `relationships_not_requested` before any request.

### interpro_find_proteins_by_domain

Description: “Find UniProt proteins carrying an InterPro or member signature. Defaults to reviewed human proteins; reviewedOnly=false includes reviewed and unreviewed proteins in the chosen taxon. Optional isFragment filters fragment annotations; false does not prove a complete canonical sequence.”

Input: required `accession`; optional `sourceDatabase`; `taxonId='9606'`; `reviewedOnly=true`; optional boolean `isFragment`; `limit=20` (positive integer, clamped to 50); optional `cursor`. GET `/protein/{reviewedOnly ? reviewed : uniprot}/entry/{database}/{accession}/taxonomy/uniprot/{taxonId}/`. Query modifiers are `page_size`, `cursor`, constant `extra_fields=is_fragment`, and `is_fragment` only when supplied, preserving explicit false. Always require a taxon; a user wanting another organism supplies its NCBI ID. `reviewedOnly=false` means all review statuses, not unreviewed-only. `isFragment=false` means not annotated as a fragment, not proof of a complete canonical sequence; omission includes both groups. Echo explicit fragment selection and bind it to cursor scope; omitted selection keeps the legacy scope unchanged. Native `extra_fields.is_fragment` is boolean when supplied; absent/null remains unknown, and all other record fields/types survive. Fragment-filtered empty guidance composes with clamp and continuation notices.

Output `{ query: { accession, sourceDatabase, taxonId, reviewedOnly, isFragment? }, proteins: complete upstream results, page: Page, sourceUrl }`. A result retains `metadata: ProteinSummary`, `entries` with full `entry_protein_locations`, `protein_length`, `entry_type`, `entry_integrated`, source database, `taxa` lineage data, and native `extra_fields`. Do not fetch each protein individually to fill absent fields. Zero hits is success with guidance to change review/taxon selection, omit an explicit fragment filter, or verify the accession with `interpro_get_entry`. A list miss cannot distinguish nonexistent entry, taxon, and valid empty intersection; do not claim which occurred. Upstream answers all three with 204; it answers 404 only when the accession is not valid for its database (`PF1` under pfam), which is `entry_not_found`. With a cursor, a 404 stays `invalid_cursor`. A 410 is `entry_withdrawn`.

### interpro_list_reference

Description: “List supported InterPro database slugs, entry types, accession routing patterns, common taxon IDs, or current release information.”

Input: required `topic` enum `databases|entry_types|accession_patterns|taxa|release`. Output `{ topic, items: ReferenceItem[], sourceUrls: string[], release?: { version, date, databaseCounts: complete /entry/ response } }`. `ReferenceItem` has required string `id` and `label`, plus optional strings `description`, `sourceDatabase`, `accessionPattern`, `example`, and `taxonId`. Each topic returns only its applicable fields: databases provide slug/label/pattern/coverage description; entry types provide enum value/label/meaning; accession patterns provide pattern/source/example; taxa provide ID/label; release returns `items: []` plus the release object. Static topics cite the official API documentation in `sourceUrls` and make zero network calls. Taxa are explicitly common examples, not an exhaustive taxonomy: human 9606, mouse 10090, rat 10116, zebrafish 7955, fruit fly 7227, nematode 6239, budding yeast 559292, Arabidopsis 3702, and E. coli 562. Explain that a well-formed identifier is not guaranteed to be assigned.

`release` makes two calls, `/utils/release/` and `/entry/`. Select the greatest numeric release tuple from the release-date map, never lexicographic order; return its supplied date and preserve all aggregate counts, including integrated/unintegrated and per-database counts. If the two responses advertise different `interpro-version` headers, fail `release_changed` rather than attaching mismatched counts. No persistent cache or bulk mirror is needed.

## Error contracts

Copy applicable rows inline into each definition's `errors` declaration; service-produced rows use `thrownBy: 'service'`. Shared service code attaches `data.reason`, status where known, and the same recovery hint. Do not share a definition-level `errors[]` constant. All declared recovery strings below are literal; include target/accession in messages rather than rewriting recovery text. Missing-record messages name the record (“InterPro could not find entry PF1 in pfam.”, likewise `set CL0016 in pfam` and `protein P04637 in uniprot`), a withdrawal message adds the deletion date and short name when supplied in a well-formed single-line form (see `interpro_get_entry`), `residue_out_of_range` states the position, protein length, and accession, and routing failures name the accession and the supplied `sourceDatabase`, plus for a mismatch the database the prefix routes to (“Accession PF00870 routes to sourceDatabase pfam by its prefix, not interpro.”, carried in `data.inferredSourceDatabase`); the same values stay in `data`, so a client showing only `content[]` sees them.

## Service and transport

Use `src/services/interpro/` for one initialized service, schemas/types, reference tables, accession routing, and the small HTTP adapter. Tool handlers validate semantics, call service methods, enrich, and return; they do not catch errors. A shared service boundary maps transport/status failures. Its methods accept request context and preserve its cancellation signal. Fetching is injected through a fetch-compatible network function for tests; test the real service, not mocked domain methods.

### HTTP/1.1 requirement

Use `node:https.request` with ALPN restricted to `http/1.1` for this upstream on both Node and Bun. A bounded live check on Node 26.10.0 (Undici 8.10.2) found that native fetch rejects an upstream 204 with `ERR_HTTP2_STREAM_ERROR`/`NGHTTP2_PROTOCOL_ERROR`: the response advertises a nonzero content length despite having no permitted body. Bun 1.4.3 native fetch accepted it. Plain HTTP/1.1 can receive surplus bytes after these headers too; reading to end can produce `HPE_CLOSED_CONNECTION`. On status 204, immediately resolve a bodyless `Response` and destroy that response/request before processing body bytes. This exact early-header behavior succeeded on both Node and Bun. Do not interpret protocol errors generally as empty results.

The adapter returns a standard `Response` after bounded body collection for non-204 statuses. Keep one timer covering headers **and** body, clear the timer and abort listener on every terminal path, destroy the exact request on cancellation, and cap decoded bytes at 4 MiB. Keep request/response error observers until teardown finishes so destroying a completed 204 cannot emit an unhandled error; settle the operation exactly once. Request `Accept: application/json` and `Accept-Encoding: identity`; reject an unexpected nonidentity content encoding as `upstream_shape_invalid`, never parse compressed bytes as JSON. Use no shared/global dispatcher mutation, no insecure parser option, and no curl subprocess. Set `agent: false` initially to avoid retaining a malformed 204 connection. Preserve headers needed for release/version checks and Retry-After. Attach error listeners before starting I/O; only the deliberately completed 204 may ignore later teardown errors. A non-204 response must reject on request, response, or premature-close errors. The adapter is the sole network seam; a fake returns standard Responses. Explicitly test its actual Node and Bun 204 path in addition to HTTP-fake service tests.

Reuse installed framework `createPacer`, `withRetry`, `defaultIsTransient`, and `httpErrorFromResponse`. `fetchWithTimeout` was examined: it calls global fetch without an injectable transport and thus cannot enforce this upstream's HTTP/1.1 requirement. Do not wrap it around the adapter or replace global fetch. The HTTP adapter earns its scope from the verified protocol defect. Special-case domain 204/404/410 and invalid continuation, then use `httpErrorFromResponse` with `captureBody: false`, explicit service name, and `codeOverride` for unhandled 3xx/4xx to satisfy the `upstream_rejected` ServiceUnavailable contract. Preserve 408/504 as Timeout, 429 as RateLimited, and 501's `retryable: false`; treat 425 as `upstream_rejected` under this server's declared contract. Attach the declared reason and retryability explicitly. This upstream is keyless: unexpected 401/403 never imply that callers should supply credentials. Only bounded validated withdrawal metadata may be copied from an error body.

### Budgets

One process-wide InterPro pacer: `minStartGapMs: 1000`, `maxConcurrent: 1`, `maxQueueDepth: 20`; `maxWaitMs` per enqueue is `min(5000, remaining call budget)`. This is a conservative client policy, not a claimed published rate limit. Every attempt, including retries, passes through it. The pacer is shared by every caller of the process, so on a public HTTP deployment with `MCP_AUTH_MODE=none` one caller filling its queue makes other callers' requests shed; such a deployment rate-limits each client at the fronting proxy.

One tool call has a 50-second wall-clock budget including all requests, parsing, pacing, and retry waits. An attempt has at most 15 seconds, bounded by the remaining call budget. Each service request uses at most one retry (`maxRetries: 1`, base delay 1000 ms, maximum delay 3000 ms), with `withRetry` around fetch + parse + validation and the pacer inside. Set each retry ladder's `deadlineMs` to the tool's remaining budget, and pass its attempt signal into both pacer and network adapter. Compose the original caller signal so cancellation keeps precedence. Before starting each additional operation, check the remaining call budget; never reset 50 seconds per request. A 200 HTML error page is retryable upstream unavailability; malformed JSON and structurally valid but incompatible JSON are `upstream_shape_invalid` with `data.retryable: false`, not raw parser exceptions that the retry default would treat as transient. Non-204 premature-close/parser/socket errors are retryable `upstream_unavailable`; the per-attempt timer is `upstream_timeout`, and caller cancellation preserves its original reason. An upstream Retry-After beyond the budget or the 3000 ms retry-delay cap fails fast, preserving the hint.

| Tool | Maximum distinct upstream operations | Maximum attempts |
|:--|--:|--:|
| search / get entry / protein discovery | 1 | 2 |
| clan | 2 | 4 |
| protein map | 1 protein + 3 match pages + optional extras = 5 | 10 |
| static reference / release reference | 0 / 2 | 0 / 4 |

Response size has its own budget: `RESPONSE_BYTE_BUDGET` in `src/services/interpro/budget.ts`, 100,000 UTF-8 bytes of the domain output serialized as compact JSON, with `jsonByteLength` and `largestFittingCount` for results that page by size. `interpro_get_clan` relationship slices and `interpro_get_protein_domains` segments use it. In the protein map the budget also bounds upstream work: a call stops reading match pages once the matches it holds fill the budget, and reads extra features only after the last match.

The `htmlparser2` dependency supplies fragment tokenization and entity decoding for readable entry descriptions. No bulk harvesting, local corpus mirror, DataCanvas, background job, or arbitrary URL input is required. Match maps and search are record-discovery/annotation workflows, not SQL workspaces.

## Decisions and limitations

- Preserve complete entry details and nested match locations. Flattening fragments loses discontinuity and can falsely label a residue inside a domain.
- Keep singular detail inputs. There is no verified multi-ID endpoint that would avoid per-accession upstream work, and current workflows already have bounded paged lists.
- Bound protein maps by bytes, in whole-match segments that can resume inside an upstream page. Titin (`Q8WZ42`) fits one 200-match page yet carries 399 KB of matches, so a page-count cap alone cannot bound a response; a position anchored to the last covered record reaches every match exactly once.
- Carry protein metadata on the first segment only, and put requested extra features after the last match. Measured on titin, repeating its 36 KB metadata stretches a 5-segment, 437 KB walk to 8 segments and 692 KB, and extras on the first segment make it 112 KB beside the first match, over the budget although no single item is; at the tail the 38 KB of extras fill the last match segment and one more.
- Keep graph projection explicit. Clan metadata already includes a potentially large relationship graph; `includeRelationships` controls both result surfaces, and member pagination remains independent.
- Page the relationship graph by offset within the 100,000-byte response budget. The `cl21453` graph alone is 2.2 MB, and an offset into a locally sorted node-then-link sequence reaches every record without a second cursor tied to the member page.
- Emit the `content[]` JSON fence compact, without indentation. Indentation on deeply nested results makes `content[]` up to 2.5× the size of `structuredContent` while adding nothing a parser or model needs.
- Omit Wikipedia thumbnails unless `includeThumbnail` is true. Included, one base64 thumbnail (about 248 KB on `PF00870`) appears three times per call, once in `structuredContent` and twice in `content[]`, and makes up nearly all of the response; the disclosed opt-in still returns the image whole.
- Use local reference vocabulary and live release data. Static identifier guidance is cheap; release counts and dates must come from current responses.
- Let upstream text shape the JSON only, never a server-written line. An error message or notice names an upstream value only when it matches a strict single-line pattern and otherwise leaves it out; the value stays whole in the JSON or error `data`. JSON-quoting a value inside the line stops block-level escapes but still renders inline Markdown and HTML such as `![x](…)` or `<img>`.
- No alternate-source guessing after a detail miss. Validated accession routing resolves standard signatures; retrying unrelated sources would hide input mistakes.

API data is release-dependent. Pagination is not a snapshot, counters are source-provided coverage counts, and extra features vary by protein. The API docs specify a maximum page size of 200; this server uses smaller search/member limits and a 50-protein discovery cap because complex cross-resource queries can time out. Unknown query parameters are silently ignored upstream, so only verified spellings are emitted. No official rate limit was found. Member-database licensing varies: [InterPro's license page](https://interpro-documentation.readthedocs.io/en/latest/license.html) covers InterPro, Pfam, PRINTS, and SFLD downloadable data under CC0; consult original owners and [EMBL-EBI terms](https://www.ebi.ac.uk/about/terms-of-use/) for other data. Attribute InterPro and the originating member database in documentation; do not claim all member data shares CC0.
